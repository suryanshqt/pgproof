# Hand-measured baseline for demo-broken

These numbers establish that the two planted index cases and the planted N+1 are
real and that their direction of effect reproduces. They are **not** a proof
bundle, not a pgproof artifact, and not a production prediction.

Every statistic below is derived from raw samples committed under
[`measurements/`](measurements/). Nothing in this file is typed by hand: the
results block is generated by `scripts/fixture_measurements.py` and a test fails
if it drifts from the raw files.

## Environment

| Item | Value |
|---|---|
| PostgreSQL | 17.11 (Debian 17.11-1.pgdg13+2) |
| Image | `postgres@sha256:67f41722b7a8cbdb868a44a4995c846eddfdc2973bccb291ce937dce88ad5675` |
| Host | Darwin, arm64 |
| Python | 3.13.5 |
| Client | SQLAlchemy 2.0.52, Alembic 1.20.0, psycopg 3.3.5, pytest 9.1.1 |
| Client pins | `pyproject.toml` and `uv.lock` in this directory |
| Session settings | `max_parallel_workers_per_gather = 0`, `jit = off`, `statement_timeout = '30s'` |

Every client version is pinned with `==` and locked. The reproduction below
installs from that lockfile and pulls the image by digest, so it cannot silently
run against a different stack than the one these numbers came from. The host
machine name is deliberately not recorded; architecture is what affects results.

Linux amd64 numbers are deliberately absent. Cross-platform reproduction is a
`BE-30` gate, not a `BE-02` claim.

## Dataset

Deterministic, derived arithmetically from `generate_series` so no `random()` or
clock call can shift a stream. See [`dataset.sql`](dataset.sql).

| Table | Rows |
|---|---|
| tenants | 200 |
| users | 20,000 |
| products | 2,000 |
| orders | 400,000 |
| order_items | 800,000 |

Status distribution: `paid` 240,000, `pending` 80,000, `shipped` 40,000,
`cancelled` 40,000. All four statuses occur in every tenant. Probe values:
tenant 7 has 2,000 orders of which 1,200 are `paid`; user 42 has 20 orders.
`SELECT sum(total_cents) FROM orders` returns `1697400000`; a different value
means the dataset is not the one these numbers came from. That checksum is
recorded inside every raw run file.

## Protocol and exact formulas

Per `docs/TECHNICAL_DESIGN.md` section 20: 3 warmups then 7 samples, timed around
statement execution plus a full fetch, in the order control A1, physical
treatment B, drift control A2. Warmups are discarded from the statistics but are
**retained in the raw files** so a reader can see what was thrown away.

Raw samples are integer microseconds, matching the "integer microseconds in raw
evidence" rule in `docs/TECHNICAL_DESIGN.md` section 4. For seven samples:

| Quantity | Definition |
|---|---|
| median | `sorted(samples)[3]` |
| Q1, Q3 | `sorted(samples)[1]`, `sorted(samples)[5]` |
| `iqr_fraction` | `(sorted(samples)[5] - sorted(samples)[1]) / median` |
| `drift_fraction` | `abs(median_a2 - median_a1) / median_a1` |
| absolute saving | `median_a1 - median_b` |
| ratio | `median_a1 / median_b` |

No p95 is reported; seven samples cannot support one.

## What reproduces and what does not

What reproduces across runs is the plan change, the index size in bytes, and a
saving of 8.96 ms to 9.60 ms for `IDX-001` and 9.52 ms to 9.74 ms for `IDX-002`,
a control-to-treatment median ratio of 34.3x to 41.7x and 39.4x to 51.7x
respectively. Those ranges are the measured spread over three runs each, not a
projection. Individual medians do not reproduce: they vary by run and by machine
load, so nothing in the results block should be quoted as *the* figure for a case.

Plan shapes, identical across every run, recorded with timing disabled:

| Case | Control A1 | Treatment B |
|---|---|---|
| `IDX-001` | `Seq Scan on orders` | `Bitmap Heap Scan on orders -> Bitmap Index Scan using ix_orders_user_id` |
| `IDX-002` | `Limit -> Sort -> Seq Scan on orders` | `Limit -> Index Scan using ix_orders_tenant_status_created` |

For `IDX-002` the sort is eliminated rather than merely accelerated, which is the
structural reason the composite index helps and is independent of any timing.

Index build took 0.043 s to 0.060 s for `IDX-001` and 0.130 s to 0.148 s for
`IDX-002`. Index size was identical in every run: 3,129,344 bytes and
16,269,312 bytes.

## Variance observations

Control-arm IQR stayed within the 20% `max_iqr_fraction` of
`docs/TECHNICAL_DESIGN.md` section 3 in all six runs: at most 10.2% for
`IDX-001` and 4.9% for `IDX-002`. A1-to-A2 drift reached 5.92% and 3.33%
respectively, so no run would be discarded as environment drift.

Treatment-arm IQR is a different matter: up to 41.9% for `IDX-001` and 19.5% for
`IDX-002`. Treatment medians are 192 to 286 microseconds, where relative spread
is dominated by timer and scheduling granularity rather than by the database.
**The IQR gate is therefore not informative for a sub-millisecond arm**, and a
verification engine that applied it symmetrically would reject sound results.
Absolute saving is the reportable quantity, which is also why
`docs/PRODUCT_SPEC.md` section 12 sorts by absolute time saved.

The practical note for `BE-25` and `BE-28`: the variance gate needs either an
absolute floor below which it is not applied, or more samples for short queries.
Six runs are not enough to characterise the tail, and this baseline does not
claim to.

## Evidence provenance

An earlier measurement session was recorded in this file as medians and IQRs
only. Its raw samples were never persisted, so those statistics could not be
independently recomputed and no number from it survives here. They were removed
rather than carried forward, and are not quoted even as context, because a
statistic whose inputs are gone is not evidence. The runs above were collected
fresh with the raw samples committed.

## Reproducing this by hand

Run from this directory. The image is addressed by digest; do not substitute a
floating version tag.

```bash
PG_IMAGE=postgres@sha256:67f41722b7a8cbdb868a44a4995c846eddfdc2973bccb291ce937dce88ad5675

docker run -d --name pgproof-fixture-pg \
  -e POSTGRES_PASSWORD=fixture -e POSTGRES_USER=fixture -e POSTGRES_DB=postgres \
  -p 55432:5432 "$PG_IMAGE"
until docker exec pgproof-fixture-pg pg_isready -U fixture -q; do sleep 1; done
docker exec pgproof-fixture-pg psql -U fixture -d postgres -c 'CREATE DATABASE demo_broken;'

# Installs the exact locked client stack, not a fresh resolution.
uv sync --all-groups --frozen

export DATABASE_URL='postgresql+psycopg://fixture:fixture@127.0.0.1:55432/demo_broken'
uv run --frozen alembic upgrade head
docker cp dataset.sql pgproof-fixture-pg:/tmp/dataset.sql
docker exec pgproof-fixture-pg psql -U fixture -d demo_broken -v ON_ERROR_STOP=1 -f /tmp/dataset.sql

uv run --frozen pytest

# Collect fresh raw evidence, overwriting measurements/.
uv run --frozen python ../../scripts/fixture_measurements.py collect \
  --dsn 'postgresql://fixture:fixture@127.0.0.1:55432/demo_broken' \
  --cases measurements/cases.json --measurements measurements \
  --image-digest "${PG_IMAGE#postgres@}" \
  --recorded-at "$(date -u +%Y-%m-%dT%H:%M:%SZ)" --runs 3 \
  --setting 'SET max_parallel_workers_per_gather = 0' \
  --setting 'SET jit = off' \
  --setting "SET statement_timeout = '30s'"

docker rm -f pgproof-fixture-pg
```

Then regenerate the derived statistics and the results block above, from the
repository root:

```bash
uv run python scripts/fixture_measurements.py summarize \
  --measurements fixtures/demo-broken/measurements --write
uv run python scripts/fixture_measurements.py check \
  --measurements fixtures/demo-broken/measurements
```

`demo-clean` reproduces with the same commands, substituting `demo_clean` for
`demo_broken`; it carries the same pins and the same `uv.lock`. It has no
`measurements/` directory because it is the control, not the baseline.

Confirm the planted schema defects directly:

```sql
SELECT conname FROM pg_constraint WHERE conrelid = 'orders'::regclass AND contype = 'f';
-- demo-broken lists fk_orders_user_id only; fk_orders_tenant_id is absent.
SELECT indexname FROM pg_indexes WHERE tablename = 'orders';
-- demo-broken lists orders_pkey only.
```
